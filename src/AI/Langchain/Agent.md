## 1. 什么是 Agent

一句话：

> **Agent = 不只是回答问题，而是会自己决定下一步做什么的系统。**

对比一下：

|      | 普通 LLM     | Agent                                              |
| ---- | ------------ | -------------------------------------------------- |
| 输入 | 一个问题     | 一个目标                                           |
| 输出 | 一个回答     | 一连串动作 + 最终结果                              |
| 行为 | 问一句答一句 | 理解目标 → 决定要不要查/调工具 → 多步推进 → 给结果 |

Agent 常见会做的事：思考下一步、调用工具、读文件、搜索知识库、调 API、写代码、执行多步任务。

它比普通问答复杂，是因为它通常**循环**做这些事：

```
看当前目标 → 决定下一步动作 → 调用工具 → 观察结果 → 再决定 → ... → 完成
```

### Agent 和 RAG 的关系

- **RAG** 是一种「先检索再回答」的**方法**
- **Agent** 是一种「会自己决定步骤并调用工具」的**系统**

两者不相等，但 **Agent 可以把 RAG 当成自己的一个工具**。例如：Agent 判断问题需要查公司制度 → 触发 RAG 检索制度文档 → 根据结果继续完成任务。

**一个直观对比**：

- 纯 RAG：用户问「年假可以跨年吗？」→ 检索制度 → 根据文档回答。一步到位。
- Agent：用户说「帮我总结请假制度，比较年假/病假/事假的区别，列成表格」→ 判断要查知识库 → 调 RAG 检索 → 提取三类信息 → 整理成表格 → 输出。多步完成。

不是所有问答都需要 Agent。

## 2. 为什么 Agent 需要工具

一句话：

> **工具 = Agent 可以调用的外部能力。**

工具不是「模型脑子里的知识」，而是运行时可以使用的额外能力，比如：搜索引擎、RAG 检索系统、数据库查询、文件读取、浏览器操作、代码执行器、计算器、邮件/日历/工单 API。

**哪些算工具，哪些不算**：

- 算工具：读文件、搜网页、查数据库、执行代码、RAG 检索器
- 不单独算工具：模型自己的推理、整理上下文、总结内容（这些是模型**能力**，不是独立工具）

### 为什么不能只靠大模型

大模型最擅长的是「根据输入生成文本」，但真实任务还需要查、算、读、写、调系统、执行操作。具体来说：

1. **模型不能直接访问外部世界**：看不到你的本地文件、最新网页、数据库、当前系统状态——没有工具就只能靠已有知识猜
2. **模型不能天然执行动作**：你让它发邮件/查库/建工单/跑代码，它只会「描述怎么做」，不会真的做
3. **模型做精确计算和查询不稳定**：数学、精确过滤、数据库查找更适合交给专门工具
4. **Agent 需要「先做，再看结果，再继续」**：没有工具就没法真正行动并观察结果

可以把 Agent 拆成两半：

> **大模型负责思考（理解目标、决定下一步），工具负责行动（执行能力、返回真实结果）。**
>
> **没有工具的 Agent，往往只剩下「会说」，不一定真的「会做」。**

## 3. Workflow vs Agent

一句话：

> **Workflow = 预先设计好的固定流程。**

如果一个系统是「先检索 → 再总结 → 再输出表格」，而且这个顺序是你**提前写死**的，那它更像 Workflow。

|        | Workflow                    | Agent                      |
| ------ | --------------------------- | -------------------------- |
| 流程   | 人提前设计好，步骤/顺序固定 | 给目标，系统自己决定下一步 |
| 灵活性 | 系统自主空间小              | 可能中途改策略、动态选工具 |
| 记忆法 | **人定流程**                | **模型定下一步**           |

**关键认知**：自动化 ≠ Agent。很多系统看起来都「自动完成任务」，但如果它只是严格按预设步骤走，那就是 Workflow，不是 Agent。很多号称 Agent 的产品，实际更像 Workflow。

## 4. 什么是 MCP

如果指的是 `Model Context Protocol`，那它**不是一个具体工具**，而是：

> **一种让模型或 Agent 连接外部能力的标准协议。**

它解决的问题是：不同工具、资源、数据源，怎么用**统一方式**接给模型或 Agent。

**最好的类比**：

> **工具像电器，MCP 像插座标准（接口标准）。** 电器是具体能力，插座标准不是电器本身，但它决定了怎么统一接入。

**为什么容易误以为 MCP 就是工具**：因为实际用时你常看到「一个 MCP server 提供很多工具，模型通过 MCP 调用它们」。更准确的说法是：MCP server 里可以包含工具，但 MCP 本身是协议和连接方式。

一句话记忆：

> **Tool = 具体能力；MCP = 接入这些能力的标准方式。**

## 5. 最小 Agent 系统由什么组成

一句话：

> **最小 Agent = 目标 + 模型 + 工具 + 决策循环 + 输出。**

| 部件        | 负责什么                                             |
| ----------- | ---------------------------------------------------- |
| 1. 目标     | Agent 要完成什么（没有目标就没有后续行动）           |
| 2. 大模型   | 思考核心：理解目标、判断下一步、决定要不要调工具     |
| 3. 工具     | 提供外部能力：读文件、搜网页、调库、调 RAG、执行代码 |
| 4. 决策循环 | 和普通一次性问答最大的区别（见第 6 章）              |
| 5. 输出     | 任务完成时把最终结果交付给用户                       |

画成结构：

```
用户目标 → 大模型判断 → 调工具 → 观察结果 → 继续判断 → 输出结果
```

**最小 Agent 不需要**：多个 Agent、复杂记忆系统、长期状态管理、规划器、MCP、工作流编排平台。这些都可以后面再加。

> Agent 最小并不复杂。它的核心不是「高级」，而是「会判断并调用工具」。

## 6. Agent 的最小运行流程

一句话：

> **接收目标 → 判断下一步 → 调用工具 → 观察结果 → 再判断 → 输出结果。**

用一个具体任务走一遍——「帮我找出项目里有哪些 TypeScript 文件，并简单说明作用」：

1. **接收目标**：明确要完成什么
2. **判断下一步**：该先做什么？要不要调工具？调哪个？→ 判断先用文件搜索工具找 `.ts`
3. **调用工具**：真的去执行查找（不是「说我要查」）
4. **观察结果**：工具返回若干 `.ts` 文件路径
5. **再判断**：这些够了吗？要不要读内容？→ 判断需要读文件才能总结
6. **继续调用工具**：调文件读取工具，拿到内容
7. **输出最终结果**：整理出有哪些文件、各自作用

**核心循环**：

> **判断 → 行动 → 观察 → 再判断。**

其中「观察工具结果」这一步特别关键——Agent 不是盲目继续，而是要根据真实结果再决定下一步。这条循环就是 Agent 和普通一次性问答的本质差异。

## 7. Agent 的常见模式

> 不是所有 Agent 都复杂，很多只是「目标 + 工具 + 决策循环」的不同组合。

| 模式                               | 长什么样                                    | 例子                                                                           |
| ---------------------------------- | ------------------------------------------- | ------------------------------------------------------------------------------ |
| **1. 单工具 Agent**                | 只有一个主要工具，模型判断何时调            | 「看看目录里有哪些 TS 文件」→ 调文件搜索 → 返回列表                            |
| **2. 多工具 Agent**                | 多个工具可选，需判断用哪个、按序调用        | 「总结 TS 文件作用」→ 搜文件 → 读内容 → 总结                                   |
| **3. RAG 作为工具的 Agent**        | 需要查资料时调 RAG，拿结果再继续            | 「总结请假制度并对比年假/病假/事假」→ 调 RAG → 提取 → 对比                     |
| **4. Workflow 外壳 + Agent 核心**  | 外层流程固定，某环节内部交给 Agent 自主判断 | 固定「收问题→检查是否查库→输出」，其中「是否查、怎么查、是否继续查」交给 Agent |
| **5. 纯 Workflow（不是真 Agent）** | 表面自动，但每步提前写死，无动态决策        | 永远走「查库→总结→输出表格」，不管问题是什么                                   |

**怎么快速区分**：

- 只有固定步骤 → 更像 **Workflow**
- 会动态选工具和下一步 → 更像 **Agent**
- 固定流程里嵌一段动态决策 → **混合模式**

**初学建议的理解顺序**：单工具 → 多工具 → RAG 作为工具 → Workflow+Agent 混合。**不要一开始就想多 Agent 系统。** 实际系统大多是混合模式，因为它更可控、更稳。

## 8. Agent 最容易踩的坑

一句话：

> **Agent 最大的问题通常不是「不会回答」，而是「不会稳定地做事」。**

| 坑                                | 是什么                           | 为什么发生                           | 后果                   |
| --------------------------------- | -------------------------------- | ------------------------------------ | ---------------------- |
| **1. 选错工具**                   | 该读文件却去查库                 | 任务理解不清、工具描述不清、边界重叠 | 结果不准、浪费调用     |
| **2. 不会用工具结果**             | 拿到结果却没真正利用             | 缺少明确的下一步判断                 | 工具白调了             |
| **3. 循环停不下来**               | 一直再查、再试、再补             | 没有清晰的完成条件                   | 成本高、延迟大、体验差 |
| **4. 该用 Workflow 却硬上 Agent** | 固定流程够用却做成 Agent         | 觉得 Agent 更高级                    | 系统更复杂、更难调试   |
| **5. 工具太多决策乱**             | 工具太多模型选不对               | 工具描述太像、功能重复               | 切换混乱、错误率上升   |
| **6. 目标太模糊**                 | 不知道什么叫「完成」             | 任务定义太宽、没输出要求             | 循环过长、输出不稳     |
| **7. 过度相信模型会自己规划好**   | 以为给够工具就能稳定完成复杂任务 | 对能力预期过高、缺约束               | 随机性大、难复现       |

**初学避坑 5 条**：

1. 工具不要一开始给太多
2. 工具描述要清楚
3. 任务目标要具体
4. **完成条件要明确**（这是「循环停不下来」的解药）
5. 能用 Workflow 解决的，不要先上 Agent

最该刻进脑子的一句：

> **不要把「模型会思考」误解成「模型会稳定执行任务」。**
>
> 简单、可控、可观察，通常比「更智能」更重要。

## 9. 总对比：Agent / RAG / Workflow / Tool / MCP

最容易混的五个词，**关键认知是：它们不在同一层。**

| 概念         | 它是什么层 | 回答的问题               | 一句话                             |
| ------------ | ---------- | ------------------------ | ---------------------------------- |
| **RAG**      | 方法       | 知识从哪里来             | 先检索资料，再生成回答             |
| **Agent**    | 系统形态   | 任务怎么一步步完成       | 为完成目标，自己决定步骤并调用工具 |
| **Workflow** | 流程设计   | 流程怎么固定执行         | 预先设计好的固定流程               |
| **Tool**     | 能力组件   | 系统具体能做什么动作     | 可调用的具体外部能力               |
| **MCP**      | 接入协议   | 这些能力怎么标准化接进来 | 让能力标准化接入的协议层           |

**它们之间的关系**：

- **Agent 和 RAG**：不相等，但 Agent 可以把 RAG 当工具
- **Agent 和 Workflow**：一个动态决策、一个固定流程，实际系统常混合
- **Agent 和 Tool**：Tool 是 Agent 做事的手脚，没有它 Agent 只能「说」
- **Tool 和 MCP**：Tool 是具体能力，MCP 是接入这些能力的协议标准
- **RAG 和 Tool**：在 Agent 系统里，RAG 常被包装成一个 Tool

**判断速查**：

- 问「知识从哪里来？」→ 在谈 **RAG**
- 问「任务怎么自己一步步完成？」→ 在谈 **Agent**
- 问「步骤是不是提前写死？」→ 在谈 **Workflow**
- 问「系统能调什么能力？」→ 在谈 **Tool**
- 问「这些能力怎么统一接给模型？」→ 在谈 **MCP**

**四个常见误区**：

1. ❌「RAG 就是 Agent」——RAG 是方法，Agent 是系统形态
2. ❌「自动化流程就是 Agent」——固定步骤更可能只是 Workflow
3. ❌「MCP 就是工具」——MCP 更像工具接入协议
4. ❌「工具越多越是好 Agent」——工具太多反而让决策混乱

压缩记忆：

> **RAG 管知识，Agent 管决策，Workflow 管固定流程，Tool 管行动能力，MCP 管接入标准。**

## 第 1 步：什么是 Agent

# 第 1 步：什么是 Agent

## 学习目标

理解：

- Agent 是什么
- Agent 和普通大模型调用有什么区别
- Agent 和 RAG 有什么关系

## 先记住一句话

`Agent = 不只是回答问题，而是会自己决定下一步做什么的系统`

普通模型更像：

- 你问一句
- 它答一句

Agent 更像：

- 它先理解目标
- 决定要不要查资料
- 决定要不要调用工具
- 决定是否继续下一步
- 最后再给你结果

## 最简单的区别

### 普通 LLM

输入：

- 一个问题

输出：

- 一个回答

### Agent

输入：

- 一个目标

输出：

- 一连串动作和最终结果

## Agent 常见会做什么

一个 Agent 常见会有这些能力：

- 思考下一步
- 调用工具
- 读取文件
- 搜索知识库
- 调 API
- 写代码
- 执行多步任务

## Agent 为什么比普通问答复杂

因为它不是只做一次生成，
而是通常会循环做这些事：

1. 看当前目标
2. 决定下一步动作
3. 调用工具
4. 观察结果
5. 再决定下一步
6. 直到完成任务

## Agent 和 RAG 的关系

RAG 不是 Agent。

Agent 也不是 RAG。

更准确地说：

- `RAG` 是一种“先检索再回答”的方法
- `Agent` 是一种“会自己决定步骤并调用工具”的系统

但是：

Agent 可以把 RAG 当成自己的一个工具或一个步骤。

例如：

- Agent 先判断问题需要查公司制度
- 然后触发 RAG 去检索制度文档
- 再根据检索结果继续完成回答

## 一个直观例子

### 纯 RAG

用户问：

“年假可以跨年吗？”

系统：

- 检索制度文档
- 根据文档回答

### Agent

用户说：

“帮我总结请假制度，并告诉我年假、病假、事假的关键区别，再列成表格。”

Agent 可能会：

1. 判断需要查知识库
2. 调用 RAG 检索相关制度
3. 提取年假、病假、事假信息
4. 整理成表格
5. 输出最终结果

这里就不只是“检索再回答”了，而是“多步完成任务”。

## 你现在应该怎么学 Agent

不要一上来就学复杂框架。

先记住 3 个核心点：

1. Agent 有目标，不只是单次问题
2. Agent 会决定步骤
3. Agent 会调用工具

## 这一课你必须记住

## 第 2 步：为什么 Agent 需要工具

# 第 2 步：为什么 Agent 需要工具

## 学习目标

理解：

- 什么叫 Agent 的“工具”
- 为什么 Agent 往往不能只靠大模型本身
- 工具和普通文本生成的区别是什么

## 先记住一句话

`工具 = Agent 可以调用的外部能力`

也就是说，工具不是“模型脑子里的知识”，
而是模型在运行过程中可以使用的额外能力。

## 工具指的是什么

Agent 里的工具，通常指这些东西：

- 搜索引擎
- RAG 检索系统
- 数据库查询
- 文件读取
- 浏览器操作
- 代码执行器
- 计算器
- 邮件、日历、工单系统 API
- 第三方业务接口

所以：

工具不一定是一个“软件界面”，
也可以是一个函数、一个 API、一个检索器、一个数据库查询接口。

## 哪些算工具，哪些不算工具

下面这些通常算工具：

- 浏览器访问或网页搜索
- 文件读取
- 数据库查询
- 代码执行
- RAG 检索器

下面这些通常不单独算工具：

- 模型自己的推理
- 模型整理上下文
- 模型总结内容

也就是说：

- “读取文件”算工具
- “搜索网页”算工具
- “分析上下文”更像模型能力，不是独立工具

## 为什么不能只靠大模型

因为大模型本身最擅长的是：

`根据输入生成文本`

但很多真实任务不只是“说”，还需要：

- 查
- 算
- 读
- 写
- 调系统
- 执行操作

这些事情如果没有工具，模型通常做不好。

## Agent 为什么往往需要工具

### 1. 模型不能直接访问外部世界

模型本身不会自动看到：

- 你的本地文件
- 最新网页
- 数据库内容
- 当前系统状态

如果没有工具，它就只能靠自己已有知识猜。

### 2. 模型不能天然执行动作

你让它：

- 发邮件
- 查数据库
- 新建工单
- 跑代码

它只会“描述怎么做”，
不会真的做。

有了工具，它才能真正执行这些动作。

### 3. 模型做精确计算和精确查询并不稳定

例如：

- 数学计算
- 精确过滤
- 数据库查找
- 报表汇总

这些更适合交给专门工具完成。

### 4. Agent 需要“先做，再看结果，再继续”

很多任务不是一步完成的。

例如：

1. 先搜资料
2. 看搜到什么
3. 再决定下一步
4. 可能继续查询或整理

没有工具，Agent 就没法真正“行动并观察结果”。

## 一个非常直观的例子

用户说：

“帮我看看这个项目里有哪些 TypeScript 文件，并总结它们的作用。”

如果没有工具：

- 模型只能猜项目结构

如果有工具：

- Agent 可以调用文件系统搜索
- 读取相关文件
- 再整理总结

这就是“工具”的价值。

## Agent 的核心不是只会想

你可以把 Agent 分成两部分：

- `思考`
- `行动`

大模型负责：

- 理解目标
- 决定下一步

工具负责：

- 执行具体能力
- 返回真实结果

所以：

`没有工具的 Agent，往往只剩下“会说”，不一定真的会做。`

## 和 RAG 的关系

RAG 也可以被看成一种工具。

例如：

- Agent 发现问题需要查知识库
- 它就调用 RAG
- RAG 返回相关文档
- Agent 再继续完成任务

所以在 Agent 系统里：

`RAG 常常是工具之一`

## 这一课你必须记住

- 工具就是 Agent 可调用的外部能力
- 大模型擅长生成文本，不擅长独自完成所有真实任务
- Agent 需要工具来访问信息、执行动作、获取结果
- 没有工具，Agent 往往只能“描述”，不能真正“完成”

# 第 3 步：什么是 Workflow

理解：

- Workflow 是什么
- Workflow 和 Agent 有什么区别
- 为什么很多系统其实更像 Workflow 而不是 Agent

## 先记住一句话

`Workflow = 预先设计好的固定流程`

也就是说：

- 第一步做什么
- 第二步做什么
- 第三步做什么

这些通常是人提前写好的。

## 最简单的理解

如果一个系统是这样工作的：

1. 先检索资料
2. 再总结内容
3. 再输出表格

而且这个顺序是你提前写死的，
那它更像 `Workflow`。

## Workflow 的特点

- 步骤固定
- 顺序固定或基本固定
- 每一步做什么是提前定义好的
- 系统自己决定的空间较小

## Agent 和 Workflow 的区别

### Workflow

- 人先把流程设计好
- 系统按流程执行

### Agent

- 给系统一个目标
- 系统自己决定下一步怎么做
- 可能中途改策略
- 可能动态选择工具

## 一个直观例子

### Workflow

“收到问题后：
先查知识库，
再调用总结模块，
最后输出 Markdown 表格。”

这里步骤是固定的。

### Agent

“帮我完成这个任务。”

系统可能会先判断：

- 要不要查知识库
- 要不要读文件
- 要不要调用浏览器
- 要不要再做下一轮查询

这里步骤不是完全提前写死的。

## 为什么很多人会混淆

因为很多系统看起来都像“自动完成任务”，
但自动不等于 Agent。

如果它只是严格按预设步骤走，
那更像 Workflow。

## 你现在应该怎么记

最短记忆法：

- `Workflow = 人定流程`
- `Agent = 模型定下一步`

## 这一课你必须记住

- Workflow 是固定流程
- Agent 是动态决策系统
- 自动化系统不一定就是 Agent
- 很多所谓 Agent 产品，实际更像 Workflow

# 第 4 步：什么是 MCP

## 学习目标

- MCP 是什么
- MCP 和工具是什么关系

## 先说结论

如果这里说的 MCP 是 `Model Context Protocol`，
那它不是一个具体工具，
更准确地说它是：

`一种让模型或 Agent 连接外部能力的标准协议`

## 最简单的理解

你可以把 MCP 想成：

- 一套统一接口规范
- 一种“模型怎么接外部能力”的约定

它解决的问题是：

`不同工具、资源、数据源，怎么用统一方式接给模型或 Agent？`

## MCP 和工具的关系

最准确的说法是：

- MCP 不是工具本身
- MCP 是让工具能够被模型统一调用的一种方式

也就是说：

- 浏览器可以是工具
- 文件系统可以是工具
- 数据库查询可以是工具
- RAG 检索器可以是工具
- MCP 是把这些能力暴露给模型的一种协议层

## 一个类比

你可以这样记：

- `工具` 像电器
- `MCP` 像插座标准或接口标准

电器是具体能力，
插座标准不是电器本身，
但它决定了怎么统一接入。

## 为什么会觉得 MCP 像工具

因为实际使用时，你经常会看到：

- 一个 MCP server 提供很多工具
- 模型通过 MCP 去调用这些工具

所以你会误以为：

`MCP = 工具`

但更准确的理解是：

- `MCP server` 里可以包含工具
- `MCP` 本身是协议和连接方式

## 在 Agent 里怎么理解 MCP

如果 Agent 需要：

- 读文件
- 查数据库
- 搜网页
- 执行代码

那 MCP 可以作为一层统一接入方式，
让这些工具能力以标准形式暴露给 Agent。

## 你现在应该怎么记

最短记忆法：

- `工具 = 具体能力`
- `MCP = 接入这些能力的标准方式`

## 这一课你必须记住

- MCP 不是具体工具
- MCP 是协议或标准接口层
- 工具可以通过 MCP 暴露给模型或 Agent
- 所以“MCP 是不是工具”更准确的回答是“不是，它更像工具接入标准”

`最小 Agent = 目标 + 模型 + 工具 + 决策循环 + 输出`

## 1. 目标

Agent 先要知道：

- 你想让它完成什么

例如：

- “帮我总结这个文件夹里的 TS 文件作用”
- “帮我查知识库并整理成表格”

没有目标，就没有后续行动。

## 2. 大模型

大模型负责：

- 理解目标
- 判断下一步
- 决定要不要调用工具
- 根据结果继续推进

工具负责提供外部能力，例如：

- 读取文件
- 搜索网页
- 调数据库
- 调 RAG 检索器
- 执行代码

1. 看当前目标
2. 判断下一步
3. 调用工具
4. 观察结果
5. 再决定下一步

这就是最小的 Agent loop。

当 Agent 觉得任务已经完成时，
需要把最终结果返回给用户。

例如：

- 一段总结
- 一张表格
- 一次查询结果
- 一个执行完成的状态

你可以把最小 Agent 画成：

用户目标 -> 大模型判断 -> 调工具 -> 观察结果 -> 继续判断 -> 输出结果

3. 调用工具查找 `.ts` 文件
4. 拿到结果
5. 整理成回答
6. 返回给用户

这已经是一个很小的 Agent 系统了。

- 多个 Agent
- 复杂记忆系统
- 长期状态管理
- 规划器
- MCP
- 工作流编排平台

这些都可以后面再加。

- `目标`：要干什么
- `模型`：负责判断
- `工具`：负责行动
- `循环`：负责多步推进
- `输出`：负责交付结果

## 这一课你必须记住

- Agent 最小并不复杂
- 它的核心不是“高级”，而是“会判断并调用工具”
- Agent 和普通 LLM 最大区别在于多步决策循环
- 工具和循环是 Agent 系统的关键

# 第 6 步：Agent 的最小运行流程

## 学习目标

理解：

- 一个最小 Agent 是怎么一步一步运行的
- 它和普通一次性问答有什么区别
- “判断 -> 调工具 -> 看结果 -> 再判断” 这条链路是怎么形成的

## 先记住一句话

`Agent 的最小运行流程 = 接收目标 -> 判断下一步 -> 调用工具 -> 观察结果 -> 再判断 -> 输出结果`

## 最小流程拆开看

### 1. 接收目标

用户先给 Agent 一个任务。

例如：

- “帮我看看这个项目里有哪些 TypeScript 文件”

这一步的作用是：

- 让 Agent 明确自己要完成什么

## 2. 判断下一步

大模型先思考：

- 这个任务该先做什么
- 要不要调用工具
- 如果要调用，应该调用哪个工具

例如在这个任务里，它可能判断：

- 先用文件搜索工具找 `.ts` 文件

## 3. 调用工具

Agent 根据判断结果，去调用对应工具。

例如：

- 调用文件搜索工具

这一步不是“说我要查文件”，
而是真的去执行查找动作。

## 4. 观察结果

工具执行完后，会返回结果给 Agent。

例如：

- 返回若干 `.ts` 文件路径

这一步很关键，因为 Agent 不是盲目继续，
而是要根据真实结果再决定下一步。

## 5. 再判断下一步

Agent 看完结果后继续思考：

- 这些文件够了吗
- 要不要继续读文件内容
- 要不要再调用别的工具

例如它可能判断：

- 需要读取这些文件，才能总结它们的作用

## 6. 继续调用工具

于是 Agent 再调用：

- 文件读取工具

然后继续拿结果。

## 7. 输出最终结果

当 Agent 觉得任务已经完成，
就把最终结果返回给用户。

例如：

- 这些 TS 文件有哪些
- 每个文件大概负责什么

## 画成最简单流程图

你可以把它画成：

用户目标
-> 模型判断
-> 工具执行
-> 返回结果
-> 模型再判断
-> 继续执行或结束
-> 输出结果

## 和普通问答的区别

### 普通问答

- 用户问一次
- 模型答一次

### Agent

- 用户给目标
- 模型判断
- 工具执行
- 模型再判断
- 可能反复几轮
- 最后才输出

## 一个非常小的例子

任务：

“帮我找出项目里有哪些 TypeScript 文件，并简单说明它们的作用。”

可能流程：

1. 接收任务
2. 判断要先找 `.ts` 文件
3. 调用文件搜索工具
4. 得到文件列表
5. 判断还需要读文件内容
6. 调用文件读取工具
7. 读取内容后整理总结
8. 输出答案

## 你现在应该怎么记

最短记忆法：

- `先定目标`
- `再做判断`
- `再调工具`
- `拿结果继续判断`
- `直到完成`

## 这一课你必须记住

- Agent 不是一步完成，而是多步推进
- 工具执行后的“结果反馈”非常关键
- Agent 的核心循环是“判断 -> 行动 -> 观察 -> 再判断”
- 这条循环就是 Agent 和普通问答的核心差异之一

## 第 7 步：Agent 的常见模式

# 第 7 步：Agent 的常见模式

## 学习目标

理解：

- 常见 Agent 模式有哪些
- 它们分别适合什么场景
- 为什么很多系统其实不是“纯 Agent”，而是混合模式

## 先记住一句话

`不是所有 Agent 都很复杂，很多 Agent 只是“目标 + 工具 + 决策循环”的不同组合。`

## 模式 1：单工具 Agent

### 长什么样

- 只有一个主要工具
- 模型负责判断何时调用它
- 调完之后整理结果输出

### 例子

用户说：

“帮我看看这个目录里有哪些 TypeScript 文件。”

系统：

1. 判断需要文件搜索工具
2. 调工具
3. 返回文件列表

### 特点

- 结构最简单
- 很适合入门
- 任务边界清晰

## 模式 2：多工具 Agent

### 长什么样

- 有多个工具可选
- 模型需要判断该用哪个工具
- 可能按顺序调用多个工具

### 例子

用户说：

“帮我总结这个项目里的 TS 文件，并说明每个文件做什么。”

系统可能会：

1. 调文件搜索工具找 `.ts` 文件
2. 调文件读取工具看内容
3. 再整理总结

### 特点

- 比单工具 Agent 更常见
- 决策难度更高
- 需要处理工具选择问题

## 模式 3：RAG 作为工具的 Agent

### 长什么样

- Agent 自己不直接懂所有知识
- 当需要查资料时，调用 RAG
- 拿到检索结果后再继续完成任务

### 例子

用户说：

“帮我总结请假制度，并比较年假、病假、事假的区别。”

系统可能会：

1. 判断需要查知识库
2. 调 RAG 检索制度文档
3. 提取关键信息
4. 整理成对比结果

### 特点

- 很常见
- 把 RAG 当成 Agent 的一个能力模块
- 适合“先查资料，再做进一步整理”的任务

## 模式 4：Workflow 外壳 + Agent 核心

### 长什么样

- 外层流程是固定的
- 某个环节内部交给 Agent 自主判断

### 例子

固定流程：

1. 先接收用户问题
2. 再检查是否要查知识库
3. 再输出结果

其中“检查是否要查知识库、如何查、是否继续查”这一段，
交给 Agent 自己判断。

### 特点

- 这是实际系统里很常见的混合模式
- 更容易控制风险
- 比纯 Agent 更稳

## 模式 5：纯 Workflow，不是真正 Agent

### 长什么样

- 表面上也在自动完成任务
- 但每一步都是提前写死的
- 没有真正动态决策

### 例子

系统永远执行：

1. 查知识库
2. 总结内容
3. 输出表格

无论问题是什么都这么走。

### 特点

- 可控
- 好调试
- 但不算真正意义上的 Agent

## 你现在应该怎么区分

最短判断法：

- `只有固定步骤`：更像 Workflow
- `会动态选工具和下一步`：更像 Agent
- `固定流程里嵌一段动态决策`：混合模式

## 初学者最该先理解哪几个

建议顺序：

1. 单工具 Agent
2. 多工具 Agent
3. RAG 作为工具的 Agent
4. Workflow + Agent 混合模式

不要一开始就去想多 Agent 系统。

## 这一课你必须记住

- Agent 有很多模式，不是只有一种形态
- 多数实际系统不是纯 Agent，而是混合模式
- RAG 很常作为 Agent 的一个工具
- Workflow 和 Agent 的边界要分清

3. 为什么很多真实系统会用 Workflow + Agent 混合模式？
4. 为什么“固定步骤自动化”不一定是 Agent？

## 第 8 步：Agent 最常见的问题

# 第 8 步：Agent 最常见的问题

## 学习目标

理解：

- Agent 最容易出问题的地方有哪些
- 为什么这些问题会出现
- 初学时应该怎么避免

## 先记住一句话

`Agent 最大的问题通常不是“不会回答”，而是“不会稳定地做事”。`

## 问题 1：选错工具

### 是什么

Agent 有多个工具时，可能挑错工具。

例如：

- 明明该读文件，却去查知识库
- 明明该查数据库，却只做网页搜索

### 为什么会发生

- 任务理解不清
- 工具描述不清
- 工具边界重叠

### 后果

- 结果不准确
- 浪费调用次数
- 任务变慢

## 问题 2：工具调用后不会正确使用结果

### 是什么

Agent 调完工具后，拿到了结果，
但没有真正理解或正确利用这些结果。

例如：

- 找到了文件列表，却没有继续读内容
- 检索到了制度文档，却回答时没用到关键句

### 为什么会发生

- 缺少明确的下一步判断
- 模型没有把“工具结果”纳入后续推理

### 后果

- 工具白调了
- 回答看起来像在乱做

## 问题 3：循环停不下来

### 是什么

Agent 一直继续：

- 再查一次
- 再试一个工具
- 再补一步

结果迟迟不结束。

### 为什么会发生

- 没有清晰的完成条件
- 模型过度谨慎
- 任务目标太模糊

### 后果

- 成本升高
- 延迟变长
- 用户体验很差

## 问题 4：本来该用 Workflow，却硬上 Agent

### 是什么

有些任务其实固定流程就够了，
但设计成了 Agent。

例如：

- 每次都固定“查 -> 总结 -> 输出”
- 根本不需要动态决策

### 为什么会发生

- 觉得 Agent 更高级
- 没分清“自动化”和“动态决策”

### 后果

- 系统更复杂
- 更难调试
- 更不稳定

## 问题 5：工具太多，决策变乱

### 是什么

给 Agent 太多工具，模型反而不容易选对。

### 为什么会发生

- 工具描述太像
- 工具功能重复
- 模型决策空间过大

### 后果

- 工具切换混乱
- 错误率上升

## 问题 6：目标太模糊

### 是什么

用户目标或者系统目标说得不清楚，
导致 Agent 不知道什么叫“完成”。

### 为什么会发生

- 任务定义太宽泛
- 没有输出要求

### 后果

- 循环过长
- 输出不稳定
- 做了很多无关动作

## 问题 7：过度相信模型会自己规划好一切

### 是什么

以为只要给模型很多工具，
它就会自然稳定地完成复杂任务。

### 为什么会发生

- 对 Agent 的能力预期过高
- 缺少约束和边界设计

### 后果

- 结果随机性大
- 很难复现
- 一会儿对，一会儿错

## 初学时怎么避免

建议你记住这 5 条：

1. 工具不要一开始给太多
2. 工具描述要清楚
3. 任务目标要具体
4. 完成条件要明确
5. 能用 Workflow 解决的，不要先上 Agent

## 最容易踩坑的一句总结

`不要把“模型会思考”误解成“模型会稳定执行任务”。`

这是 Agent 入门最重要的现实认知之一。

## 这一课你必须记住

- Agent 难点在稳定执行，不只在回答
- 工具选择、结果利用、停止条件都很关键
- 并不是所有自动化都适合做 Agent
- 简单、可控、可观察，通常比“更智能”更重要

## 复习问题

1. Agent 为什么容易选错工具？
2. 为什么“调了工具”不等于“真正用了工具结果”？
3. 为什么没有完成条件时，Agent 容易停不下来？
4. 为什么很多任务其实更适合 Workflow？

## 第 9 步：Agent 和 RAG、Workflow、Tool、MCP 的总对比

# 第 9 步：Agent 和 RAG、Workflow、Tool、MCP 的总对比

## 学习目标

把这些概念一次性理顺：

- Agent
- RAG
- Workflow
- Tool
- MCP

## 先记住一句话

`这几个词不在同一层。`

它们分别属于：

- 方法
- 系统形态
- 流程设计
- 能力组件
- 接入协议

所以很多人会混淆，是因为它们在一个系统里经常同时出现。

## 1. RAG 是什么

`RAG = 先检索资料，再生成回答的方法`

它的重点是：

- 查资料
- 用资料回答

它回答的是：

`知识从哪里来`

## 2. Agent 是什么

`Agent = 为了完成目标，自己决定步骤并调用工具的系统`

它的重点是：

- 有目标
- 会判断下一步
- 会调用工具
- 会多步推进

它回答的是：

`任务怎么一步步完成`

## 3. Workflow 是什么

`Workflow = 预先设计好的固定流程`

它的重点是：

- 步骤提前定义
- 顺序基本固定
- 系统自己决定空间小

它回答的是：

`流程怎么固定执行`

## 4. Tool 是什么

`Tool = Agent 或模型可调用的具体外部能力`

例如：

- 读文件
- 搜网页
- 查数据库
- 调 RAG
- 执行代码

它回答的是：

`系统具体能做什么动作`

## 5. MCP 是什么

`MCP = 让模型或 Agent 接入外部能力的一种标准协议`

它的重点是：

- 统一接入
- 统一暴露工具和资源
- 统一调用方式

它回答的是：

`这些能力怎么标准化接进来`

## 放到一张脑图里

你可以这样理解：

- `RAG`：一种知识获取与回答方法
- `Agent`：一种会动态决策的系统形态
- `Workflow`：一种固定流程组织方式
- `Tool`：具体可调用能力
- `MCP`：把 Tool 接给模型/Agent 的协议层

## 它们之间怎么相互关系

### Agent 和 RAG

- RAG 不等于 Agent
- Agent 也不等于 RAG
- 但 Agent 可以把 RAG 当成一个工具

### Agent 和 Workflow

- Workflow 是固定流程
- Agent 是动态决策
- 实际系统里经常混合使用

### Agent 和 Tool

- Tool 是 Agent 做事的手和脚
- 没有 Tool，Agent 往往只能“说”，不能真正“做”

### Tool 和 MCP

- Tool 是具体能力
- MCP 是接入这些能力的协议标准

### RAG 和 Tool

- 在 Agent 系统里，RAG 常常会被包装成一个 Tool

## 一个非常实用的判断表

### 如果你问的是：

“知识从哪里来？”

更像在谈：

- `RAG`

### 如果你问的是：

“任务怎么一步步自己完成？”

更像在谈：

- `Agent`

### 如果你问的是：

“步骤是不是提前写死？”

更像在谈：

- `Workflow`

### 如果你问的是：

“系统具体能调什么能力？”

更像在谈：

- `Tool`

### 如果你问的是：

“这些能力怎么统一接给模型？”

更像在谈：

- `MCP`

## 最容易混淆的地方

### 误区 1

“RAG 就是 Agent”

错。

RAG 是方法，Agent 是系统形态。

### 误区 2

“自动化流程就是 Agent”

错。

固定步骤更可能只是 Workflow。

### 误区 3

“MCP 就是工具”

错。

MCP 更像工具接入协议。

### 误区 4

“有很多工具就一定是好 Agent”

错。

工具太多反而更容易让 Agent 决策混乱。

## 一句话总总结

你可以这样把它们压缩记住：

- `RAG` 管知识
- `Agent` 管决策
- `Workflow` 管固定流程
- `Tool` 管行动能力
- `MCP` 管接入标准

## 这一课你必须记住

- 这些概念不在同一层
- 一个真实系统里，它们常常会同时出现
- 先分清层次，再谈怎么组合

4. 为什么 RAG 在 Agent 系统里常常会变成一个 Tool？

## Agent 总复习

# Agent 总复习

这份文档只保留后期复习最重要的内容。

## 一、Agent 是什么

最简单定义：

`Agent = 为了完成目标，自己决定步骤并调用工具的系统`

一句话记忆：

`Agent 管的是“任务怎么一步步完成”。`

## 二、Agent 和普通大模型调用的区别

普通 LLM：

- 你问一句
- 它答一句

Agent：

- 你给一个目标
- 它判断下一步
- 调工具
- 看结果
- 再判断
- 最后完成任务

一句话记忆：

`普通模型偏单次回答，Agent 偏多步执行。`

## 三、Agent 最小系统需要什么

最小 Agent = 5 个部分：

1. 目标
2. 大模型
3. 工具
4. 决策循环
5. 输出

一句话记忆：

`目标 + 模型 + 工具 + 循环 + 输出`

## 四、Agent 最小运行流程

最小运行流程：

1. 接收目标
2. 判断下一步
3. 调用工具
4. 观察结果
5. 再判断
6. 输出结果

Agent 的核心循环就是：

`判断 -> 行动 -> 观察 -> 再判断`

## 五、为什么 Agent 需要工具

因为大模型最擅长的是：

- 生成文本

但真实任务还需要：

- 读文件
- 搜网页
- 查数据库
- 调 RAG
- 执行代码

没有工具，Agent 很多时候只能“说怎么做”，不能“真的做”。

一句话记忆：

`工具负责行动，模型负责思考。`

## 六、工具是什么

工具就是：

`Agent 可调用的外部能力`

常见例子：

- 文件读取
- 浏览器/搜索
- 数据库查询
- RAG 检索器
- 代码执行器

注意区分：

- `读文件` 算工具
- `分析上下文` 不算工具，更像模型能力

## 七、Workflow 是什么

最简单定义：

`Workflow = 预先设计好的固定流程`

一句话记忆：

- `Workflow = 人定流程`
- `Agent = 模型定下一步`

## 八、MCP 是什么

如果说的是 `Model Context Protocol`：

`MCP = 让模型或 Agent 接入外部工具和资源的标准协议`

它不是具体工具。

一句话记忆：

- `Tool = 具体能力`
- `MCP = 接入标准`

## 九、Agent 的常见模式

### 1. 单工具 Agent

- 只有一个主要工具

### 2. 多工具 Agent

- 有多个工具可选

### 3. RAG 作为工具的 Agent

- 需要查知识时调用 RAG

### 4. Workflow 外壳 + Agent 核心

- 外层固定流程
- 局部动态决策

### 5. 纯 Workflow，不是真正 Agent

- 步骤固定
- 没有动态选择下一步

## 十、最容易混淆的地方

### 1. Agent 和 Workflow

Workflow：

- 固定步骤
- 不强调动态决策

Agent：

- 会根据目标和中间结果决定下一步

一句话记忆：

- `固定步骤 = 更像 Workflow`
- `动态决策 = 更像 Agent`

### 2. Agent 和 RAG

RAG：

- 先检索再回答的方法

Agent：

- 为了完成目标动态决策的系统

关系：

- RAG 可以成为 Agent 的一个工具

一句话记忆：

- `RAG 管知识`
- `Agent 管决策`

### 3. Tool 和 MCP

Tool：

- 具体能力

MCP：

- 让这些能力标准化接进模型/Agent 的协议

一句话记忆：

- `工具像电器`
- `MCP 像插座标准`

## 十一、Agent 最容易出问题的地方

最常见问题：

- 选错工具
- 调了工具但不会用结果
- 循环停不下来
- 本来该用 Workflow，却硬上 Agent
- 工具太多，决策变乱
- 目标太模糊
- 过度相信模型会自己规划好一切

一句话记忆：

`Agent 最大的问题通常不是不会说，而是不会稳定地做事。`

最该刻进脑子的一句：

`不要把“模型会思考”误解成“模型会稳定执行任务”。`

## 十一-A、初学避坑 5 条

1. 工具不要一开始给太多
2. 工具描述要清楚
3. 任务目标要具体
4. 完成条件要明确（这是“循环停不下来”的解药）
5. 能用 Workflow 解决的，不要先上 Agent

一句话记忆：

`简单、可控、可观察，通常比“更智能”更重要。`

## 十二、什么时候更适合 Workflow，不适合 Agent

如果任务是：

- 固定步骤
- 重复执行
- 不需要动态决策

那通常更适合 Workflow。

一句话记忆：

`能用固定流程解决的，就不要先用 Agent。`

## 十三、后期复习只记这些句子

- `Agent = 为完成目标，自己决定步骤并调用工具`
- `Agent 管决策`
- `工具负责行动，模型负责思考`
- `Workflow 是固定流程`
- `MCP 是工具接入标准，不是工具本身`
- `RAG 可以是 Agent 的工具`
- `固定步骤更像 Workflow，动态决策更像 Agent`
- `Agent 最大问题是稳定执行，不只是回答`
- `不要把“会思考”误解成“会稳定执行”`
- `完成条件要明确，否则循环停不下来`
- `能用 Workflow 解决的，就不要先上 Agent`
